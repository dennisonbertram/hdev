Hetzner · Claude Code · systemd

hdev

Plan on your laptop. Each slice of the plan goes to a coding agent on its own throwaway Hetzner VM, started under systemd so it keeps working after you close the lid. It comes back as a branch and a pull request.

Topology

→ SSH
the slice brief, your subscription token, and your skills
← SSH
status notes, log lines, and answers from the running agent
→ HTTPS
the branch, then the pull request
durable — outlives the job ephemeral — gone when you reap the isolation boundary

What one job does

  1. 01
    Split the plan
    Every ## Slice: heading becomes its own job. Slices run in parallel from the same base commit, so each one has to stand alone.
  2. 02
    Boot a VM from the snapshot
    The toolchain is already baked in, so the box is ready in 39 seconds instead of roughly 3 minutes.
  3. 03
    Create the job user
    Claude Code refuses --dangerously-skip-permissions as root. The agent user gets passwordless sudo, so nothing is actually blocked.
  4. 04
    Ship credentials over SSH
    Never through cloud-init — Hetzner stores user-data and serves it from the metadata service. On the box the GitHub token lives in a credential helper, so it never appears in a remote URL.
  5. 05
    Ship the skills
    efficient-fable is copied from your own ~/.claude/skills. Per job, not baked into the image, so editing a skill here takes effect on the next submit.
  6. 06
    Detach under systemd, and return
    systemd-run --unit=hdev-job --uid=agent. This is the moment the laptop stops mattering. Close the lid.
  7. 07
    Orchestrate, don't type
    The agent loads the skill, then delegates to implementer, tester and reviewer, keeping the plan and the commit for itself.
  8. 08
    Push a branch, open a PR
    The slice brief becomes the PR body. If the agent changed nothing, it says so and pushes nothing.
  9. 09
    Reap
    Jobs never delete their own VM — that would need a Hetzner write token sitting on a box that runs an agent with open permissions. hdev reap does it from your side instead.

Talking to a job while it runs

hdev status — costs nothing

Reads the notes the orchestrator keeps for itself. No model call. This answers “how is it going” most of the time.

## Plan
1. [done]        implementer — strip dashes
2. [in progress] tester — npm test
3. [pending]     reviewer — diff vs brief

hdev ask — the agent itself

Resumes the job's own conversation with --fork-session, so the answer comes from the agent that did the work, with its full context, while its own thread stays untouched. Safe to use mid-run.

hdev ask <job> "why skip the cache?"
→ 4.6 s round trip

hdev ask -c <job> "stop before the PR"
→ -c continues the real thread

Where this is thinner than it looks. The fork was verified against an idle session. Behaviour while the worker is mid-write to its own transcript has not been tested. Codex has no fork at all, so hdev ask refuses on a running Codex job.
